What Did AI Cost Us This Quarter?
Per-department chargeback on Red Hat OpenShift AI.

Track AI inference costs by department using MaaS Gateway API keys, Perses dashboards, and MLflow tracing — no manual instrumentation required.
By Markell Rawls & Suhas Kashyap | Red Hat

The question nobody can answer

Three departments share your AI inference platform. Engineering sends code review prompts through a 27-billion-parameter model every five seconds. Marketing generates campaign copy on the same model every twelve seconds. Support handles customer questions on a smaller, cheaper model every twenty seconds. At the end of the quarter, finance asks what each team spent.

If the answer involves a spreadsheet, a Slack thread to the platform team, and two weeks of detective work, the problem isn't your AI stack. It's visibility. We built a working demo on Red Hat OpenShift AI that answers that question in under a minute, using data the platform already collects. No separate billing tool. No manual instrumentation. Here's how.

Why per-department cost tracking matters

When multiple teams share a GPU cluster for inference, someone pays for it. Without per-department attribution, the bill goes to the platform team, and nobody has a reason to be efficient.

Our demo's sample quarterly report shows what that looks like in practice. Three departments generated 79,420 inference requests and consumed 634 million tokens over a quarter, totaling $14,200 in estimated cost. That's the easy number. The useful number is that Marketing was running at 32% GPU utilization — meaning 68% of their allocated GPU capacity sat idle. At $50,000 per GPU node per year, that's roughly $34,000 in annual idle capacity that nobody would catch without per-department metrics.

The difference between "AI costs $14,200 this quarter" and "Engineering consumed 60% on the premium model, Marketing is underutilizing their allocation, and Support is using the right model for their workload" is the difference between a cost center and a managed platform.

How the observability stack works

The cost attribution system runs on four components, all available in OpenShift AI 3.4 and later:

MaaS Gateway sits in front of your model servers. Each department gets its own API key, created in the OpenShift AI Dashboard under Gen AI Studio. The gateway routes requests by model and authenticates them by key. That key becomes the identity boundary for everything that follows.

vLLM or llm-d serves the models. In our demo, we run two: a primary model (gemma4) shared by Engineering and Marketing, and a secondary model (qwen35-9b) for Support. The serving layer reports token counts per request back to Prometheus.

Prometheus via the Cluster Observability Operator (COO) auto-scrapes token consumption metrics from the model servers. No sidecar injection, no custom exporters, no configuration. When you deploy a model through MaaS, Prometheus starts collecting per-user, per-model token metrics automatically.

Perses dashboards visualize the data at OpenShift Console > Observe > Dashboards > Usage. You can filter by subscription (API key) to isolate one department, or filter by model to see cost differences between workloads.

On top of this, MLflow traces every inference request at the application level. Each trace contains the department name, the prompt (truncated), the model, input and output token counts, latency, and calculated cost. These traces live in the OpenShift AI Dashboard under MLflow.

API keys as cost boundaries

The cost isolation in this system comes from one mechanism: one API key per department.

When a platform team creates three API keys in Gen AI Studio, each key shows up as a distinct subscription in the Perses Usage dashboard. Every token consumed under that key is attributed to that department. Every request is traceable to the team that made it.

Cost attribution doesn't require changes to application code. If a team is already calling the MaaS Gateway with an API key, their usage is being tracked. The data is already there.

What the dashboards tell you

Perses: the platform view

The Perses Usage dashboard answers the platform team's questions: total tokens consumed across all departments, per-user breakdown by API key, per-model token distribution, and filtering by subscription or model.

In our demo running three departments for five minutes, we see Engineering consuming roughly 60% of tokens, Marketing at about 25%, and Support at about 15%. The breakdown appears in real time — no aggregation delay, no batch processing.

MLflow: the application view

MLflow adds context that Prometheus can't capture. Each request creates a two-span trace structure: a parent AGENT span with the department name and prompt, and a child CHAT_MODEL span with the model, token counts, latency, and cost. 

AGENT span: engineering_agent
├── input: "Review this Go module for concurrency issues..."
├── department: engineering
└── CHAT_MODEL span: generate_response
    ├── model: gemma4
    ├── input_tokens: 487
    ├── output_tokens: 312
    ├── cost: $0.02143
    └── latency: 2.4s

This means you can answer not just "how much did engineering spend?" but "what were they spending it on?" The traces show the specific prompts — code reviews, API design questions, unit test generation — and the cost of each one.

The cost model

Cost attribution needs a cost model. We define per-model pricing as cost per 1,000 tokens, split between input and output:

Model Input cost per 1K tokens Output cost per 1K tokens
gemma4 (primary) $0.015 $0.045
qwen35-9b (secondary) $0.005 $0.015

The cost calculation in the load generator is straightforward: 

COST_PER_1K = {
    "gemma4":    {"input": 0.015, "output": 0.045},
    "qwen35-9b": {"input": 0.005, "output": 0.015},
}

def calculate_cost(model, input_tokens, output_tokens):
    rates = COST_PER_1K.get(model, {"input": 0.01, "output": 0.03})
    return (input_tokens / 1000 * rates["input"]) + \
           (output_tokens / 1000 * rates["output"])

The input/output split matters. Engineering's workloads are heavy on both — long code context as input, detailed analysis as output. Support uses short customer questions and short answers on a model that costs 3x less per token. That cost difference is invisible if you're only tracking total tokens.

Get started

The demo runs on OpenShift AI 3.4 or later. Clone the demo-chargeback repository, configure your environment, and generate traffic: 

cp .env.example .env
# Edit .env: set MAAS_GATEWAY, API keys, MLflow URI

python generate-load.py --duration 5

Within five minutes, your Perses and MLflow dashboards will show per-department cost attribution data. The repository includes prompt sets for all three departments, on-cluster deployment via Kubernetes Job, and a presenter walkthrough for live demos.

What's coming in OpenShift AI 3.5

The current approach gives you dashboard-level visibility. In OpenShift AI 3.5, a metering webhook pushes per-request token events directly to your billing system — user, model, input tokens, output tokens, latency, and request ID. That moves chargeback from "check the dashboard" to "it's in your invoice automatically."

Try it yourself

The demo is open source and runs from a laptop or on your cluster. Start with the demo-chargeback repository on GitHub, or learn more about OpenShift AI observability in the product documentation.
